# v1.3.0 — local preparation candidate

**Status: unreleased working-tree candidate.** This file records the current
preparation scope. It is not a stable support boundary: no release branch,
signed tag, GitHub tag verification or GitHub Release is claimed. The canonical
changelog remains under `Unreleased` until the release gates are complete.

## Candidate scope

- Separate catalog, taxonomy, customer, Buyer order, Sales order and logistics
  permissions so one broad legacy permission cannot authorize unrelated
  mutations or reads. Align the built-in Tenant Administrator and Sales grants
  through additive migration.
- Add Buyer-membership-scoped catalog favorites, personal delivery addresses,
  company registration and provider-backed saved payment methods.
- Add one fixed global five-business-day delivery lead policy for Buyer and
  Sales order creation and changes in `America/Lima`, without a holiday
  calendar or Workspace override, plus receipt-time lot temperature readings
  for Warehouse/BOM review.
- Restrict Dispatch visibility to the Buyer account, Sales account and
  warehouse grants relevant to each backed Dispatch.
- Add optional per-Tenant business-database provisioning and routing for locally
  enabled capabilities. Central identity, control and onboarding remain shared;
  production cutover is not claimed. Accept standard and URL-safe Base64 worker
  credentials while restricting generated `.pgpass` entries to safe characters.
- Extend password-reset delivery and rate limiting, and strengthen Tenant/
  Workspace row-level security and database-role checks.

## Explicit Buyer response contract change

`GET /api/v1/client-accounts/me` removes `contactPerson`, `contactEmail`,
`phone` and `buyerMembershipId` to reduce personal-data and internal membership
identifier exposure. The Owner explicitly approved retaining this privacy
correction in the v1.3.0 candidate and documenting its wire-contract impact.
Consumers that read these four fields must stop doing so. The Buyer registration
POST keeps its separate response schema; contact fields remain nullable when an
account has multiple historical Buyer memberships.

This is a real response incompatibility. The approval records Product intent;
it does not make the change SemVer-compatible or turn the release gate green.
The repository policy requires a compatible release line for breaking changes.
Do not publish v1.3.0 until the compatibility gate is resolved by the authorized
release decision.
