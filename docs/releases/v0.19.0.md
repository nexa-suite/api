# Nexa API v0.19.0

**Release boundary:** 2026-09-30

**Publication:** Consumer support requires the locally and GitHub-verified
annotated SSH-signed `v0.19.0` tag and
[GitHub Release](https://github.com/nexa-suite/api/releases/tag/v0.19.0).

This release boundary closes the accepted module and persistence boundaries while
preserving v0.18.0 consumer contracts and canonical Product semantics. It does
not establish Product Acceptance, System Acceptance or Production Readiness.

## Module and persistence boundaries

- Exactly eleven canonical business contexts remain. All are closed Spring
  Modulith modules with explicit named interfaces and allowed dependencies.
  The direct business dependency graph is acyclic; module verification passes.
- Published in-process contracts carry immutable identifiers, snapshots,
  query results and established errors. Infrastructure, controllers and
  internal aggregates remain private. Consumer source ports and SQL-free
  runtime composition preserve dependency direction and local transactions.
- The baseline's 51 distinct foreign business consumer/table SQL pairs are
  removed. Owner queries now supply customer relationships, governance facts,
  inventory policy, order claims, fulfillment evidence, receivable/payment
  facts and document sources. The technical payment-event adapter also uses
  owner queries instead of direct payment/receivable SQL.
- Per-table ownership is explicit, including legacy physical placement,
  global reference data and shared technical event/idempotency tables.
  Fitness checks reject foreign business SQL, unknown ownership and SQL in
  runtime boundary composition.
- Existing FEFO eligibility, deterministic locks, RLS scope, CAS, worker
  claims, idempotency, rollback, reconciliation and immutable evidence remain
  covered by repository integration tests. Page lookups are batched; existing
  Catalog and Sales query budgets pass.

The [closure record](../architecture/v0.19-boundary-closure.md) lists every
removed pair, replacement contract, dependency and retained SQL classification.

## External transport hardening

- Configured SMTP outside local/test requires secure transport and HTTPS
  reset/invitation links.
- Configured durable S3-compatible storage requires an HTTPS endpoint without
  user information. Local/test fixtures retain their existing HTTP support.
- Google Routes requires HTTPS at the trusted `routes.googleapis.com` host;
  arbitrary endpoints cannot receive the configured API key.
- A Stripe custom API base is rejected outside local/test fixtures.

Configuration errors do not expose configured secret values. The
[ASVS matrix](../security/asvs-5-level-2-matrix.md) records these controls as
PARTIAL: startup validation is evidenced, while deployment TLS and live provider
configuration remain unverified.

Release preparation also applies same-line Jackson BOM patches, 2.21.6 and
3.1.6, for [CVE-2026-68497](https://github.com/FasterXML/jackson-databind/security/advisories/GHSA-q4xh-88c3-wmh7).
The retained HIGH/CRITICAL image gate identified the previously managed
2.21.5 and 3.1.5 databind artifacts. Focused regression coverage accepts normal
XML duration values and requires oversized numeric strings to fail through
stream constraints in both Jackson generations. This dependency correction
does not change Product authority or grant acceptance.

## Database and HTTP compatibility

No database migration required; physical schema preserved.

The highest Flyway version remains V107. No published migration was edited.
Fresh PostgreSQL creation, upgrade from exact published v0.17.1/V100 and the
complete RLS inventory pass. The restricted runtime role and pooled scope
cleanup remain verified.

There are no removed endpoints, new endpoints or breaking HTTP changes.
Existing 280 paths and 332 operations remain. The repository generator changes
only OpenAPI `info.version` from `0.18.0` to `0.19.0`; parameters, responses and
schemas remain unchanged. Runtime/snapshot parity and compatibility against
`develop`, v0.17.1 and v0.18.0 pass. Deprecated compatibility routes remain.

## Acceptance limitations

Existing Web and Operations identity/context/catalog/logistics backend
contracts remain compatible. No Web browser acceptance journey or physical
Mobile acceptance was executed by this API release gate. Backend Buyer contracts
do not implement Buyer Mobile. Operations client implementation and verification
remain separately evidenced in the Mobile repository.

Web/Mobile Product Acceptance remains separate. Tracking/location history, contact
providers, generic offline sync, RFID/industrial scanning authority, telemetry,
batch/field-visit and unresolved carrier-handoff semantics were not invented.
Canonical Blueprint and Mobile Report files were not modified.

Production TLS, real provider connectivity, deployment behavior, capacity,
Product Acceptance and System Acceptance require separate evidence. This
candidate does not claim all stories implemented or zero vulnerabilities.
