# Nexa API v0.17.0 — Mobile V1 Core Contracts

Mobile V1 backend core contracts ready for client integration.

This is a pre-v1 backend candidate release. It does not claim complete Nexa
V1, Production Ready status or full Mobile Product acceptance.

## Approved scope delivered

- Basic physical identifier resolution for SKU/GTIN and lot/batch references.
- FEFO/picking scan validation with explicit outcomes, stale/over-pick
  protection, split multi-lot support and controlled FEFO override.
- Physical picking allocation binding, preserving the existing fulfillment
  lifecycle and legacy partial-delivery compatibility.
- Ephemeral Delivery QR handoff with hashed token, bounded TTL, one-time use
  and relationship/authorization checks.
- Immutable Buyer receipt/discrepancy fact; delivery state is not mutated by
  the handoff fact.
- Provider-neutral native push subscription registration, rotation,
  disable/unregister, durable outbox routing, retry/dead-letter foundation and
  deferred provider behavior.
- Evidence compatibility hardening required by the delivered contracts.

## Database and reliability

- Additive Flyway migrations V93-V100. V1-V92 are untouched.
- Tenant/workspace FORCE RLS, composite foreign keys, append-only protections,
  constraints and identifier/expiry indexes are preserved and extended only
  for the approved contracts.
- Idempotency keys, request hashes, optimistic/CAS checks, deterministic lock
  ordering, durable delivery claims/leases and safe replay outcomes protect
  retry-sensitive and scarce-resource operations.
- Legacy reservation, commercial backing, logistics fulfillment, physical
  allocation, dispatch and transfer lot-lock paths share the canonical
  SKU/warehouse/expiration/received/lot order. Parent warehouse and storage
  zone locks are acquired in the same deterministic order before physical
  picking validation.
- Push delivery is at-least-once. A crash after provider success can still
  duplicate delivery; the stable delivery key enables provider-side
  deduplication when the provider supports it. The shipped provider-neutral
  adapter records `DEFERRED` until a real native provider is configured.

## Explicit exclusions

GPS/live tracking/ETA/geofencing/route optimization; generic offline sync;
advanced transfer or receiving scanning; advanced GS1 parsing; RFID, scanner,
printer/label, Bluetooth and IoT/temp sensors; advanced Buyer quick actions;
general chat; rich notification campaigns/analytics; Mobile conflict center;
full dispute management; returns/RMA; new accounting; SUNAT; advanced BI; and
client-owned camera, torch, haptics, Maps, phone, WhatsApp and email UX.

## Candidate status and residual boundaries

PASS for backend core-contract integration by Website, Platform, Portal,
Operations Mobile and Buyer Mobile teams. This release remains a large V1
backend candidate, not v1.0.0, not Production Ready and not full Mobile Product
acceptance.

Real native push provider delivery, operational production credentials,
cloud topology, SLO, RPO/RTO, backup-restore rehearsal, retention and responder
readiness remain separate operational gates. The V100 claim-state check allows
legacy `CLAIMED` rows without a claim token for compatibility; the normal
adapter always writes the fenced token and tests cover claim release/replay.

SCM tag, GitHub Release and back-merge identifiers are recorded in the final
release handoff.
