# Nexa API v0.6.0

## Summary

Consolidated Identity, tenant administration, security and commercial foundation work into the API release line. Intermediate planned versions were never published.

## Highlights

- IAM/session lifecycle with persistent PostgreSQL sessions, refresh-family revocation and durable authentication throttling.
- Organization Administration, Client Accounts and Purchase Requests with tenant/workspace scope, audit events, optimistic concurrency and idempotent submission.
- Server-authoritative catalog and price snapshots; Sales Order domain readiness without persistence or HTTP.

## Functional capabilities

- Authentication, session, Catalog, Organization, Workspaces, Memberships, Client Accounts and Purchase Requests.
- Purchase Request lifecycle: draft, submit, review, adjustment, approval, rejection and cancellation.
- Problem Details, pagination, filters, `ETag`, `If-Match` and `Idempotency-Key` contracts.

## Architecture

- Sales is separated into Client Account and Purchase Request bounded responsibilities.
- Presentation DTOs map to Application models; Domain remains framework-free; explicit ports isolate JDBC adapters.
- Transactions are declared at Application service boundaries. No generic repository or generic adapter was introduced.

## Security

- Bearer authentication revalidates the persistent session and verified tenant/workspace membership.
- Refresh and sign-out enforce surface, cookie and Origin policy; security headers are emitted by the runtime.
- Buyer access is client-account scoped; internal Sales permissions do not grant Buyer access; secrets and tokens are not stored in browser artifacts.

## API changes

- Added Client Account and Purchase Request HTTP DTOs, mappers, query/command controllers and validation.
- OpenAPI documents Bearer, refresh-cookie, Problem Details, pagination, filters and concurrency headers. Sales Order, Warehouse, Logistics and Invoicing endpoints remain absent.

## Database migrations

- Flyway remains authoritative for `iam`, `tenant_management` and `sales` schemas, including Client Accounts, Purchase Requests, lifecycle events and idempotency records.
- Existing applied migrations are not rewritten or repaired blindly; canonical runtime and fresh PostgreSQL validation are required.

## Docker

- Modern Compose builds API, Platform, Portal and PostgreSQL from source with health checks and PostgreSQL kept on the internal network.
- Legacy Compose remains an isolated reference runtime and is not modified by this release.

## Validation

- API: `./mvnw clean test` and `./mvnw clean package`; Testcontainers PostgreSQL integration; OpenAPI generation/parseability; protected runtime flow.
- Platform and Portal: asset validation, tests, optimized production build, npm audit and browser route checks.
- Release evidence records tests, runtime status, Flyway validation, security matrix, OpenAPI paths, source Compose build and tracked-file hygiene.

## Breaking changes

- Catalog and commercial resources require authenticated, verified tenant/workspace access.
- Mutating Client Account and Purchase Request operations require `If-Match`; submission requires `Idempotency-Key`.
- Sales HTTP contracts no longer expose the former broad controller or Application models directly.

## Upgrade notes

- Start from the published API `v0.4.0` history and run Flyway validation against the target database before startup.
- Configure canonical PostgreSQL, RSA key, allowed Origin and local bootstrap variables; do not copy local credentials into tracked files.

## Known limitations

- No Sales Order persistence or HTTP workflow.
- No inventory reservation.
- No dispatch.
- No invoicing.
- No cache tier.
- No production deployment.
- Final pixel-level Vue parity remains ongoing. Structural parity has been advanced for implemented surfaces.
