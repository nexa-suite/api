# API v2.0.0 — release candidate

This candidate is not a published release. Publication requires the repository release gates, a signed verified tag and a GitHub Release.

## Contract impact

The global delivery lead policy counts five Monday–Friday business days after the current date in America/Lima, without a holiday calendar. API validates supplied delivery dates and revalidates on submission. Requests previously accepted with a shorter lead time now receive HTTP 400; consumers must use the policy endpoint and handle validation errors. A legacy Purchase Request draft may be created without a date, but cannot be submitted without a valid date. Existing idempotent replays remain replayable.

The authenticated `GET /api/v1/buyer/delivery-lead-policy` returns the minimum business days, earliest calendar date and timezone. Historical persisted lead settings are not deleted, but no longer govern this rule.

## Password recovery

- Route native Buyer (`PORTAL`) password-reset requests to the existing Platform recovery page. The reset token is delivered in the URL fragment, and the browser request is bound to an allowed Origin before token consumption. Expired and reused tokens are rejected; unknown-account responses remain generic and requests are rate-limited.
- PR #129 (`e0dc950bc299b935d76dc2f0d7760d7a6a4c663b`) passed its required API CI, including PostgreSQL integration and OpenAPI compatibility. The merge into `develop` is `acbb76f56deba09fcb0ee31ea6854238dcb7486b`; release-branch checks and post-merge checks must pass on their own final commits.
- The recorded local browser run preceded final hardening for missing versus empty `Origin`; it does not verify that final distinction end to end. Live HTTPS configuration, deployed email delivery, and a deployed recovery page have not been verified.

## Buyer client-account self response privacy

`GET /api/v1/client-accounts/me` no longer returns `contactPerson`,
`contactEmail`, `phone` or `buyerMembershipId`. This is an intentional
privacy-related contract break in this v2.0.0 candidate. Consumers must remove
reads of these properties from the Buyer account response. For a Buyer's own
personal profile, use the existing `GET` and `PATCH /api/v1/me/profile`
contract; its `phone` is personal profile data, not the business account phone.
The separate Buyer Portal already has a `/portal/profile` page wired to those
profile operations. This candidate documents the API change; it does not claim
that every consumer has migrated. Business contact data (`contactPerson`,
`contactEmail` and the business phone) has no Buyer self-service replacement in
this candidate, so consumers should not expect to read or manage it until that
capability is defined and delivered. The Buyer membership identifier is not a
client-facing field on this endpoint.

## Verification and limits

### Generated OpenAPI and consumer migration

The runtime-generated contract is now committed instead of the earlier candidate
snapshot. PostgreSQL-backed `OpenApiContractIT` passes against that generated
contract without enabling snapshot writing. This establishes runtime/snapshot
parity; it does not establish backward compatibility.

The strict comparison with the PR base
`689be612d96079feb02a155fbe76d829a10bdeb1` identifies 429 findings. They include:

- 248 previously optional parameters documented as required, including
  `If-Match` and `Idempotency-Key`. Consumers must send the returned entity version
  for versioned writes and retain the same idempotency key when retrying a write.
- 58 removed `200` response declarations in operations that declare creation,
  acceptance or no-content responses. Consumers must use the endpoint's exact
  success contract and must not require a JSON body for a `204` response.
- Request/response schema corrections for Buyer Purchase Request drafts, Buyer
  delivery receipts and catalog pricing preview. Pricing preview accepts `items`
  and `asOf` through `CatalogPricingPreviewRequest`; public contact requests keep
  their separate `Request` schema. Review these operation-specific changes against
  the committed snapshot and regenerate generated SDKs before adoption.
- Authentication requirements, `X-Resume-Token` header declarations, removed
  framework-generated query parameters and the Buyer account `404` media type.
  These findings are included in the exact Owner-reviewed migration; the gate
  rejects unrecorded changes.

The Product Owner approved the exact migration on 2026-11-02; see the
[manifest and baseline counts](../openapi/migrations/README.md) and
[decision record](https://github.com/nexa-suite/api/pull/133). This is not a
GitHub PR review, proof of consumer migration, or a blanket compatibility claim.

Buyer Mobile commit `d1bf0fef2ed76e89cd26c16bf3e07905b5e9b18f` consumes
`minimumDeliveryLeadBusinessDays`, `minimumAllowedDeliveryDate` and `timezone`
from the delivery-policy response. Its focused repository/view-model/widget
checks passed. That evidence does not establish compatibility for every route.

### Cloud deployment boundary

The existing Render service selects profile `s3`. Tenant-bound routing and the
Buyer personal-address, favorite and conversation capabilities in this candidate
are wired only for profile `local`; Purchase Request routes fail closed without
an available Tenant business database. Deploying this source to Render does not
enable those flows. Cloud Tenant credentials, provisioning and routing must be
implemented and verified before presenting them as connected cloud workflows.
Selecting the local development profile on Render is not a deployment solution.

The existing Neon central database was observed at Flyway V145. Upgrading this
candidate requires 43 central migrations through V189 (V187 is absent), with
owner preparations between migration checkpoints and separate Tenant database
migration verification. These remain future validation steps; observation of the
existing database was read-only. A validation child branch was created before changing
the existing database; no production migration is evidenced here.

The integrated H-01 tree passed the API PR checks, PostgreSQL-backed Maven verification and connected Flutter and Web tests at their stated commits. PR #129 passed its checks on its stated HEAD; its integration is documented above. Final release-branch checks, integration with final client versions, required human review and post-merge verification remain required. This source candidate does not establish Product Acceptance, System Acceptance, physical-device acceptance or Production Readiness.
