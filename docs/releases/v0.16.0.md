# Nexa API v0.16.0

Backend V1 Closure & Mobile Readiness.

## Scope

- Closed the API Backend V1 implementation boundary without adding Product V1
  scope, a bounded context, or a mobile aggregate.
- Preserved the canonical eleven Blueprint bounded contexts and the existing
  V1-V91 Flyway history.
- Added only transport-level native-client readiness over the existing BC-01
  session model. Browser sessions continue to use the surface-specific
  HttpOnly refresh cookie and Origin policy; native sessions use the explicit
  rotated opaque refresh-token header.
- Added startup enforcement for a dedicated least-privilege PostgreSQL runtime
  login separate from the Flyway migrator.
- Made the MinIO/S3-compatible integration test an explicit part of the CI
  integration gate.
- Corrected the local Compose launcher to activate the configured observability
  profile, keeping API readiness and telemetry dependencies aligned.

## Residual audit

- Tenant-wide and user-wide high-cardinality collections use bounded page/size
  contracts or explicit caps, with deterministic ordering; this includes
  catalog, customer, commitment, dispatch, document, evidence, notification,
  audit, change-feed and session reads.
- Resource-scoped histories (price history, document events and dispatch
  lifecycle/handoff events) retain their released list contracts because they
  are authorized through the parent aggregate and are not cross-tenant search
  surfaces. Queries use stable aggregate/time ordering; no cosmetic pagination
  break was introduced in v0.16.
- Static geography/reference lists and account-address lists are bounded by
  their controlled reference/aggregate cardinality. No unbounded critical
  tenant search path was justified by the audit.

## Explicit exclusions

Mobile Product delivery is not claimed. This release does not introduce a
Mobile bounded context, Flutter/Kotlin/Swift architecture, push provider,
device-trust semantics, QR/GPS/IoT flows, mobile-only aggregates or offline
business-success semantics. Cloud, SLO, RPO/RTO, retention, provider and
responder decisions remain open in the Production Gate.

## Database and migration policy

No new Flyway migration was justified for this closure. V1-V91 remain
untouched; runtime-role enforcement is deployment configuration plus startup
validation, and the existing fresh/upgrade migration suite remains the source
of database evidence.
