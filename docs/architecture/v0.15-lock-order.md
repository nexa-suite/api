# v0.15 transaction and lock order

All commands are tenant/workspace scoped and execute in one application
transaction. The following order prevents cross-context deadlocks:

1. Resolve and authorize the current tenant/workspace and actor.
2. Acquire the operation-scoped PostgreSQL advisory lock using tenant,
   workspace, actor, operation and idempotency key.
3. Lock the owning aggregate/resource row with `FOR UPDATE`.
4. Lock child rows in deterministic identifier/order sequence.
5. Apply the owner context mutation and append its immutable event/outbox fact.
6. Call the next context only through its public application contract.
7. Record the command idempotency result last; commit all facts atomically.

The critical v0.15 paths are:

- start fulfillment: Sales Order → Inventory Backing → physical lots →
  Fulfillment → Sales Order status;
- shortage resolution: Fulfillment → physical allocation release →
  discrepancy resolution → BC-07 financial adjustment;
- dispatch: Fulfillment → physical allocation consumption → Delivery;
- delivery outcome: Delivery → Fulfillment lines → BC-07 adjustment →
  Sales Order status.

## Resource lock matrix

| Command boundary | Deterministic lock order | Serialized identity | Atomic consequence |
|---|---|---|---|
| Start canonical fulfillment | Sales Order → commercial backing → physical-allocation command → eligible lots → fulfillment | tenant/workspace + sales order + idempotency key | lot-level allocation and backing consumption cannot be observed separately |
| Legacy reservation/dispatch compatibility | Sales Order → legacy reservation/dispatch resource | tenant/workspace + sales order | legacy and canonical execution paths cannot create two active deliveries |
| Picking/packing/staging/handover | Fulfillment → fulfillment lines → physical-allocation lines | tenant/workspace + fulfillment + command key | each transition is monotonic and quantity bounded |
| Delivery attempt/final outcome | Delivery → Fulfillment → fulfillment lines → physical allocation → BC-07 adjustment | tenant/workspace + delivery + command key | delivery history, quantity resolution and financial consequence commit together |
| Financial adjustment | source Sales Order (when applicable) → receivable → adjustment idempotency claim | tenant/workspace + source + receivable + adjustment key | post-payment cancellation/reduction validates the Sales Commitment source before advancing the receivable |
| Payment application | Payment → receivable → BC-07 application contract | tenant/workspace + payment/idempotency key | provider fact is preserved and receivable application is delegated |

When a command spans multiple rows, every collection is ordered by the
stable persisted identifier.  Provider calls and asynchronous workers run
outside the transaction that claims or records their durable idempotency
state; they are never retried as an unsafe database side effect.

Adapters never call another context's SQL tables as an alternative to its
public contract. Legacy tables are read only where the owning context exposes
that compatibility projection.
