## Remaining semantic authority finding

Customer Terms runtime authority remains OPEN. BC03 owns the canonical
`catalog_management.customer_terms` facts, while BC02's
`ClientAccountPersistenceAdapter` still implements BC03 `CustomerTermsQuery`
from legacy `sales.client_account.payment_condition`. The current canonical
representation provides `credit_days` but does not prove the exact legacy
`code`, `creditAllowed` and `dueDays` mapping. Zero-day integration fixtures do
not establish payment-mode semantics. Closing that finding requires an
accepted representation decision; architecture/persistence test success does
not declare canonical boundary closure complete.

## Closed ownership model

The API retains exactly eleven immutable business-context identifiers, BC01
through BC11, as mapped in
[`bounded-context-module-map.md`](bounded-context-module-map.md). No new context
or context split is introduced by this closure. Physical schema names remain
storage details: table exceptions are explicit in
[`canonical-sql-ownership.tsv`](canonical-sql-ownership.tsv), including BC02
customer relationship tables under `sales`, BC07 credit and receivable tables
under `payments`, BC10 notification preferences under `tenant_management`,
global reference data, and shared event/idempotency tables.

That manifest enumerates actual tables created by published Flyway migrations
through V107. Each table has one evidence row; there are no schema wildcards or
runtime allowlists. A newly created migration table without a row is an open
ownership-evidence failure.

Business SQL stays with the table owner. Cross-context consumers use narrow
same-process public APIs carrying only required identifiers, immutable
snapshots, query results, and established errors. Contracts do not expose SQL,
JDBC rows, persistence entities, or another context's aggregate. Runtime
boundary bootstrap is a composition layer: it adapts typed facts between owner APIs and
does not query business tables.

## Boundary contracts and cycle removal

The closure uses consumer-owned source ports where dependency direction needed
to be inverted. `bootstrap.runtime.boundaries` composes these contracts from
owner APIs without taking persistence authority:

- BC05 declares `InventoryCommercialSource` and `InventoryFulfillmentSource`.
  The runtime bridge maps Sales Commitment's `SalesOrderFulfillmentQuery`
  (`get`, `getForUpdate`) and Fulfillment & Delivery's
  `FulfillmentInventoryQuery` (`hasFulfillment`, `hasActiveDispatch`,
  `physicalAllocationForDelivery`) into immutable inventory snapshots.
- BC07 declares `FinancialAdjustmentSource`, with a scoped sales-order claim
  and successful-payment fact. Runtime composition supplies them from Sales
  Commitment and Payments owner contracts.
- BC08 declares `PaymentSalesSource` for payable-subject facts. Runtime
  composition delegates it to `SalesOrderFulfillmentQuery`.
- BC01 declares `TenantExternalConfigurationSource`; runtime composition maps
  notification preference operations to BC10 `NotificationPreferenceAccess`
  and transaction counts to BC04 `SalesUsageQuery.countTransactions`. BC10 owns
  notification preference vocabulary, defaults and validation. BC01's tenant
  settings compatibility DTOs carry values only and receive normalized values
  through that composition.
- BC03 declares `CatalogClientAccountPort`; its runtime adapter composes BC02
  `CustomerAccountQuery.findUnfilteredReferenceForMembership`,
  `findActiveBuyerDetails`, and `findActiveDetails`.

Other owner boundaries include BC01 `WorkspaceDirectory` and
`WorkforceDirectory`; BC02 `CustomerAccountQuery` and
`CustomerMembershipQuery`; BC03 `SellableSkuQuery` and
`CatalogDocumentSourceQuery`; BC04 `SalesDocumentSourceQuery` and
`SalesOrderFulfillmentQuery`; BC06 `FulfillmentDocumentSourceQuery` and
`FulfillmentInventoryQuery`; BC07 `ReceivablePaymentAccess`; BC08
`PaymentDocumentSourceQuery`; and BC09 `BusinessEvidenceQuery`. Their narrow
records preserve the scoped IDs, status/version, and other value fields
required by each caller. They do not authorize a consumer to issue owner SQL.

## Preserved behavior and query bounds

The refactor changes SQL ownership and composition, not existing Product or
HTTP semantics. Implementations retain existing typed errors, authorization,
tenant/workspace predicates, idempotency, version checks, and public response
shapes. In particular:

- Physical allocation keeps the existing idempotency, Sales Order claim,
  backing/lot lock order, lot eligibility and temperature predicates, FEFO and
  deterministic ordering, `FOR UPDATE OF l`, and shortage behavior. Inventory
  policy parameters are prepended for the CTE without changing remaining SQL
  argument order.
- Dispatch continues to claim the Sales Order before locking its own
  reservation. Reservation expiry uses `WorkspaceDirectory.scanAfter` in
  100-row keyset pages inside the existing transaction and RLS cross-scope
  setup/cleanup flow. Existing worker release/expiry behavior remains intact.
- Notification preference version/CAS and defaults remain in the notification
  owner adapter; BC10 validates category/channel values for both preference
  facades. BC01 retains transport/application DTOs only and delegates validation,
  reads, writes and defaults through runtime composition. Draft list count, Buyer
  membership/account scope, non-submitted filter, sort, page, and error behavior
  remain; only the redundant account join is removed.
- Catalog list availability remains within its existing four-query maximum:
  `findWithPolicies` carries typed policy facts with each page row, and direct
  availability lookups batch owner policy facts once. No per-row public list
  calls were added. Dispatch headers are fetched in one batch after paging;
  business-card snapshots use batched order headers and historical customer
  facts by native ID.
- Payment page receipt numbers and receivable facts are owner-batched. Sales
  buyer membership resolution changes from one join to two batched owner
  queries; an empty customer relationship list avoids the membership query.

## Explicit direct module dependencies

Each BC root declares `allowedDependencies` for the named interfaces it uses.
The direct business graph is acyclic; shared technical contracts are additional
explicit dependencies:

```text
BC01 -> shared
BC02 -> BC01, BC03
BC03 -> BC01
BC04 -> BC01, BC02, BC03, BC05, BC07, BC08
BC05 -> BC01, BC03, BC11
BC06 -> BC01, BC02, BC04, BC05, BC07, BC09, BC11
BC07 -> BC01, BC02, BC11
BC08 -> BC01, BC02, BC07, BC09
BC09 -> BC01, BC02
BC10 -> BC01, BC02
BC11 -> BC01
```

Consumer source ports invert additional fact dependencies through SQL-free
`bootstrap.runtime.boundaries` composition. This preserves one process and the
existing local transaction; it does not create a broker, remote call or saga.
`access-contracts`, `access-values` and `governance-queries` publish selected BC01
contracts and immutable values. Selected type annotations use `propagate=false`;
internal aggregates, infrastructure and controllers remain unexported. The
purity checks allow only Modulith export metadata, and continue to reject
Spring runtime, persistence, transport, JWT and SQL dependencies in pure code.

## Retained cross-schema SQL classification

Physical schemas remain unchanged. Every retained qualified table reference is
listed in the ownership manifest; there are no OPEN or undocumented exceptions.

- BC01 may read `iam` and `tenant_management` tables it owns.
- BC02 owns the legacy `sales.client_account`, `sales.client_account_address`
  and `sales.client_account_membership` tables.
- BC07 owns the eight prescribed credit/receivable/adjustment tables under
  `payments`; BC08 owns the separate payment lifecycle tables there.
- BC10 owns `tenant_management.notification_preference`, in addition to its
  `notifications` tables.
- `reference_data.department`, `province`, `district` and `road_type` are
  explicit GLOBAL_REFERENCE tables.
- Shared technical events are only `integration.change_event`, `inbox_event`
  and `outbox_event`. Shared technical idempotency support is explicitly listed
  per table: `catalog_management.command_idempotency`; the three `logistics`
  command tables; `notifications.push_subscription_command_idempotency`;
  `payments.reconciliation_refund_idempotency`; the five `sales` idempotency
  tables; the three `tenant_management` invitation/registration/workspace
  idempotency tables; and the two `warehouse` command idempotency tables.
  This classification grants no access to foreign business tables. Existing
  scopes, payload fingerprints, CAS, response replay and claim fencing remain.

No migration was added, and no published migration was edited.
